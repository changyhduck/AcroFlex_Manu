# AcroFlex 手冊草稿撰寫

## 目的與範圍

依使用者指定章節的 `index.md`、實際產品圖片與操作截圖，撰寫同目錄的 `content.md`。使用繁體中文、臺灣用語、明確邏輯與精確字眼，面向實際安裝、管理與維護人員。

此任務產生文件來源。只有使用者另行要求時，才產生網頁、修改網站程式、提交 Git 或發佈。

## 產品與事實依據

- AcroRed 為產品公司；官方網站為 https://www.acrored.com/ 。
- AcroCube 指實體超融合主機硬體；AcroFlex 指由一台或多台 AcroCube 組成的超融合系統；AcroFlex Client 與 AcroCube Client 的名稱依實際管理介面使用，不混用。
- 先讀取專案 README、手冊寫作規範、父章 `index.md` 與本節 `index.md`。鄰近章節可協助統一術語、排版與交叉參照，不作為新功能的唯一證據。
- 使用者明確提供的規格與適用版本是撰寫依據；截圖只能證明可見的名稱、值與狀態，不能證明未顯示的操作結果。需要外部佐證時查閱官方對應頁面，確認版本與型號，並在文末保留直接連結及查閱日期。
- 官方行銷說明不能直接當成特定版本、授權或組態下的操作保證。資料彼此衝突時指出衝突；影響正確操作的關鍵缺口須請使用者確認，其餘可繼續撰寫。
- 不自行補出密碼、預設值、規格、埠號、RAID 行為、容錯能力、權限要求、重開機行為或復原指令。無依據的內容以「待確認」標記，並列入文末待確認事項。

## 撰寫流程

1. 確認章節編號、名稱、目的、讀者、綱要及操作順序；若已有 `content.md`，先閱讀並保留仍適用的已審閱內容。
2. 列出 `index.md` 引用的圖片及章節素材。標準位置為 `assets/images/` 與 `assets/screenshots/`；若專案使用 `asset/` 或其他位置，以實際路徑為準，不擅自搬動素材。
3. 使用圖片檢視工具查看每張將引用的圖片，辨識頁面、頁籤、欄位、按鈕與狀態。不可僅依檔名推測畫面。文字太小、裁切、遮蔽或圖片缺失時，標記具體缺口，不虛構欄位。
4. 將綱要各項轉成完整說明，以「目的 → 前置條件 → 操作 → 預期結果 → 驗證」形成讀者可執行的流程；純硬體或介面介紹改用組態、區域與欄位解說。
5. 將圖片放在對應操作或說明附近，解釋圖中重點。截圖的 IP、容量、名稱與狀態以範例標示；不把範例值當成環境通用設定。
6. 寫入 `content.md` 後，核對綱要覆蓋、圖號、圖片路徑、欄位名稱與前後邏輯；回報完成位置及尚待確認的關鍵內容。

## 文章格式

沿用專案現有格式；無既定格式時使用下列 frontmatter：

```yaml
---
number: "3.2"
title: "章節名稱"
status: draft
source: index.md
---
```

標題格式為 `# 3.2. 章節名稱`，編號與名稱取自綱要。文章內使用 `##`、`###` 組織內容，不另創正式子章節編號。`status: draft` 代表內容待審閱，不因完成撰寫就標為已發佈。

按主題需要選用：簡介與適用範圍、前置條件、介面或硬體說明、操作步驟、結果驗證、注意事項、疑難排解、參考資料與待確認事項。不建立沒有實質內容的空段落。

- 以標準 Markdown 撰寫，避免依賴特定網頁 DOM、CSS、內嵌 JavaScript 或絕對本機路徑。
- 圖片使用相對於 `content.md` 的路徑，例如 `![AcroFlex Client 主畫面](assets/screenshots/infra_main_page_chinese.png)`；保留原檔名大小寫。
- 圖片下方使用獨立圖說，例如 `圖 3.2-1　AcroFlex Client 主畫面。`；本節圖號連續，正文可用圖號參照。更新既有文章時維持圖文參照一致。
- 替代文字說明圖片所呈現的介面、動作或狀態，不只重複檔名。僅引用與本節相關的圖片，不為使用全部素材而重複插圖。
- 欄位表可包含「欄位／用途／限制或範例」，依已確認內容選擇欄位；若值未知，不建立推測的預設值欄。
- 除列舉 UI 原文外，統一產品名稱、單位、術語與數值格式。UI 原文字樣須精確保留，操作按鈕可用粗體，IP、路徑、命令與輸入值用行內程式碼。

## 專業操作說明要點

- 每一步明確指出所在頁面、操作對象、動作與必要輸入；一個步驟聚焦一個主要動作。避免「依需要設定」「操作即可完成」等缺少判斷條件的敘述。
- 說明按鈕送出後是否為背景任務、需要等待何種狀態，以及如何確認成功。未知等待時間不填入任意秒數；點選按鈕不等同作業成功。
- 版本、型號、角色權限與授權條件已知時明確註記；未知時不宣稱適用全部部署。
- 刪除、還原、角色轉換、韌體更新、關機及網路變更等操作，依實際風險在操作前說明影響、必要前置條件、備份或維護安排。僅寫有依據的復原方式；未知復原程序須標記待確認。
- 區分原因、現象與處理方式。疑難排解先提供可驗證的檢查與預期結果，避免盲目重試會改變系統的操作。
- 截圖若含帳密、Token 或客戶識別資訊，指出素材問題並請提供遮蔽版本；不將敏感值抄入正文。IP 依專案素材政策處理，使用合適的示例位址，不改動原圖。
- 規格計算需列出公式、單位、假設與適用範圍；不可將估算當成設備銘牌值或安裝保證。
- 說明操作本身，不加入宣傳口號或無條件承諾，例如「絕不遺失資料」「永不中斷」。

## 完成檢查

- 綱要各項都有對應內容，已知條件與待確認內容清楚分開。
- 使用的圖片均已實際檢視，所有相對路徑可解析，圖號與引用一致。
- 文字能讓目標讀者辨識操作對象、完成步驟並驗證結果。
- 命令、預設值與欄位行為有依據；外部補充資料保留來源與版本適用限制。
- Markdown 標題、表格、清單與結尾換行符合專案規範；既有內容修改不覆蓋無關的使用者變更。
